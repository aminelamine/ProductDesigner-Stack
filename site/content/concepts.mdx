# Core concepts

The five ideas that make PDS Stack different from every other AI workflow.

## The memory

The part that compounds, and the reason the stack exists.

```
memory/
├── identity.md        the visual story, the floor, and what this product is NOT
├── design-system/     registries extracted from Figma — tokens, components, text styles
├── references/        annotated screenshots — WHY it works, what we took, what we did not
├── directions/        every direction judged — retained AND refused, with the reason
└── decisions/         structural decisions, design-shaped
```

Reading order in the DIRECTION phase, and never the reverse: `identity` → `directions` →
`design-system` → `references` → `decisions`. Starting from references before the directions
already settled is how you repropose what was refused.

<Callout type="info">
  A refused direction is worth more than a retained one. It is the only artefact that stops the
  next brief re-suggesting what this product has already rejected. Nothing is ever deleted from
  `directions/`.
</Callout>

`setup` builds the memory from Figma, from your code, from four declared answers — or, when there
is nothing at all, through a **genesis** that writes `identity.md` with you. No empty store ever
blocks a phase: it is signalled and filled.

## The Quality Brief

A creative contract, written and approved **before the scope is frozen** and before anything is
generated. It captures visual direction, three defining words, constraints, and references, read
out of the memory. This is the system's core gate — it turns taste from a hope into a requirement.

## The three lanes

Ceremony matches stakes. The lane is the first question asked, and the default is Sketch.

| Lane | When | Phases | Human gates |
| --- | --- | --- | --- |
| **Sketch** *(default)* | explore, iterate — the 80 % | DIRECTION → PRODUIRE | 1 |
| **Standard** | a screen or component going to review or dev | all four | 2 |
| **System** | it touches the design system | all four + written decision | 3 |

Hard budget: three human gates, about twelve steps. Any rule that does not fit is cut, not
documented. In Sketch there is no spec file, no score, no written decision — relaunching is
cheaper than documenting.

## The cycle

```
DIRECTION → CADRE → PRODUIRE → JUGER + MÉMORISER
```

Direction first, and the scope is framed **by** it — not before it. Production goes to Figma by
default, to code when `modules.code` is on. Judgment writes back into the memory the next
direction reads.

## Two verdicts, never averaged

Conformance is a /20 computed against what was written — spec, design system, ADRs. Direction is
binary, blocking, and the designer alone renders it. Neither overrides the other, and they are
never merged into a single number.

<Callout type="warning">
  P-001 cycle 1 scored 18/20 = SHIPPED and was rejected outright by the designer. With four
  conformance dimensions and no aesthetic one, that was the only possible outcome. The case is now
  a regression test for the gate itself.
</Callout>

A refused direction goes back to **DIRECTION**, never to the builder. It is not a list of bugs to
fix; it is a direction to retake.

## Hard constraints

These are enforced by the agents, not left to discipline:

- No code without `statut: VALIDATED` in the spec
- No code without Quality Brief approval
- TypeScript strict — zero `any`, zero `@ts-ignore`
- Components cap at 150 lines
- `/components/ui/` is read-only (Shadcn owns it)
- Consult the ADR index before any architecture or dependency decision

## Guardrails

A constraint an agent honours is only as strong as the agent's attention. Three of the above are
also checked by tooling, so they hold under a careless operator too.

Two git hooks, installed on request and bypassable with `--no-verify`:

- **`commit-msg`** — product code needs a `Ref: feature_<id>` trailer, and the spec it names must
  be `VALIDATED`. A commit that can't reference a spec is outside the frozen scope, which is a new
  RAY cycle, not a commit.
- **`pre-commit`** — `any` and `@ts-ignore`, the line cap from your `STACK.md`, and `tsc --noEmit`.
  Type errors are filtered to the files in the commit, so pre-existing breakage elsewhere warns
  instead of blocking. `hook_exclude` in `STACK.md` lists paths the guards should ignore.

## Proof over inspection

Every acceptance criterion a machine can decide carries exactly one assertion, and BOB runs it
before handing over — no test framework is installed, and there is no coverage target. Criteria come
back `proven`, `unproven` (visual, with the reason) or `failed`. **"Believed OK" is not a status**:
that phrasing is precisely how a real defect once reached ANALYZER instead of being caught at build
time. ANALYZER re-runs the assertions rather than trusting the output it was handed, and deducts a
point per code-decidable criterion shipped without one.

Assertions live in a `[feature].check.ts` next to the logic they prove. If the project already has
a runner (vitest, jest, `node:test`), BOB uses it. If it has none, **nothing gets installed** — the
file compiles through the TypeScript compiler `strict_mode` already requires:

```bash
npx tsc lib/[feature]/*.ts --outDir .proof --module commonjs --target ES2022 --strict --skipLibCheck
node .proof/[feature].check.js
```

`.proof/` is disposable, and check files use a local equality helper rather than `node:assert` —
that import needs `@types/node`, which plenty of front-end projects do not carry.

<Callout type="info">
  That command is in the docs because the first version of this rule was not runnable. It said "run
  it with whatever the project can already execute", which in a `moduleResolution: bundler` project
  is nothing. [Pulse run 3](/self-test) found it after three failed attempts.
</Callout>
