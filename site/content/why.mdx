# Why PDS Stack

A dev has `package.json`, a lockfile, a linter, CI. A designer has a Figma file and their memory.

**PDS Stack versions that memory.** A design system extracted from Figma, references annotated with
*why* they work, and every direction the designer has already validated or refused — read by every
agent, on every feature, before anything is produced.

**The memory is the product. The workflow is thin.**

## The inversion

| Conventional AI dev | PDS Stack |
| --- | --- |
| 1. Prompt | 1. Read the memory |
| 2. Generate | 2. Approve the direction |
| 3. Ship | 3. Frame the scope *around* it |
| 4. ~~Design review (if there's time)~~ | 4. Two verdicts — one of them yours |
| _Taste arrives last. Rework is the norm._ | _Taste leads, and it accumulates._ |

## Four constraints

### Direction before scope — not after

The direction brief is approved **before** the scope is frozen. In V3 it was the other way round,
and the two gates could contradict each other while both passed. The scope is now framed *by* the
direction, so they cannot disagree.

### Taste compounds, not trivia

`memory/directions/` records every direction submitted to judgment — **retained and refused**, with
the reason. A refused direction is worth more than a retained one: it stops the next brief
reproposing what was already judged wrong on this product. Nothing is ever deleted from it.

### Two verdicts, never averaged

Conformance is a /20 the system computes against what was written. Direction is binary and the
designer alone renders it. A delivery can be 20/20 and refused — and the system says exactly that.

> This is not theoretical. P-001 cycle 1 scored 18/20 = SHIPPED and was rejected outright by the
> designer. With four conformance dimensions and no aesthetic one, that was the only possible
> outcome. It is now a regression test for the gate itself.

### Ceremony matches stakes

Three lanes, default **Sketch**: direction plus production, one gate, no spec file, no score.
Hard budget: three human gates, about twelve steps. Any rule that does not fit is cut, not
documented.

## Time and cost are the same problem

In a prompt-and-pray flow, time and token spend go to the same place: the loop. Generate, look at it, realize it's not the right direction, regenerate. That loop — not the generation itself — is where processing time and token cost actually accumulate. A wrong direction caught after a build is expensive twice: once in tokens spent producing it, once in tokens spent redoing it.

Every gate in PDS Stack exists to cut that loop short. The direction brief is approved as text,
before BOB writes a line of code — correcting direction in prose is cheap; correcting it in a
shipped build is not. The frozen scope means BOB never regenerates a feature from a moving
target. Both ANALYZER verdicts gate the commit, so rework happens once, against a spec and a
judgment, instead of in open-ended back-and-forth.

None of this is a token-metering feature — PDS Stack doesn't track your bill. It's a structural bet: validate direction once, cheaply, before the system spends real processing time building it. Fewer wasted generations is fewer tokens burned and less time waiting, as a side effect of the gates existing at all.

## The cycle

```
(recherche)   DIRECTION            CADRE             PRODUIRE          (handoff)   JUGER + MÉMORISER
───────────   ─────────────────    ───────────────   ──────────────    ─────────   ──────────────────
EVE, optional brief, 5 dimensions  scope, framed     Figma (default)   Figma →     ① conformance /20
              read from memory/    BY the direction  code (module)     dev spec    ② direction — binary
                     ⏸ gate ①            ⏸ gate ②                                        ⏸ gate ③
```

Research and handoff never gate anything — they feed the phases that do. EVE preps interviews,
synthesizes research and restitutes findings before DIRECTION exists to read them. After
PRODUIRE, a handoff skill turns an approved Figma frame into a dev-ready spec when the
implementation leaves this cycle for someone who wasn't in the room.

| Lane | When | Phases | Human gates |
| --- | --- | --- | --- |
| **Sketch** *(default)* | explore, iterate — the 80 % | DIRECTION → PRODUIRE | 1 |
| **Standard** | a screen or component going to review or dev | all four | 2 |
| **System** | it touches the design system | all four + written decision | 3 |

A refused direction goes back to **DIRECTION**, never to the builder. It is not a list of bugs to
fix; it is a direction to retake.
