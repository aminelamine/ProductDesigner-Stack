The design stack for product designers / v4.1.1 / MIT

Design is the quality gate.

A dev has a lockfile, a linter, CI. A designer has a design file — Figma, Penpot, Framer — and their memory. PDS Stack versions that memory — design system, references, and every direction you have judged — and reads it before anything is produced. The memory lives in files. The conversation is disposable.

01 The inversion

The designer's creative judgment is the system's quality gate — not one input among many.

Conventional AI dev
  1. Prompt
  2. Generate
  3. Ship
  4. Design review (if there's time)

Taste arrives last. Rework is the norm.

→
PDS Stack
  1. Direction
  2. Approve the brief
  3. Build to spec
  4. Score & learn

Taste leads. Code is the execution.

i.

Direction before execution

A direction brief — visual direction, three defining words, constraints, references — is explicitly approved before the scope is frozen and before anything is generated.

ii.

Scope is sacred

Scope freezes the moment a spec hits VALIDATED. Additions require a fresh RAY cycle. No silent creep, no moving targets.

iii.

System memory

ANALYZER writes a learning after every verdict. RAY reads the three most recent before the next spec — improvements compound.

A small studio
that never sleeps.

    Runs the deployment checklist and coordinates the hand-off so nothing slips between done and live.

    /ship
03 The cycle

One command. Four phases. Each in its own session.

/pds asks the lane first — Sketch by default — then drives the cycle and stops at every gate for your decision. It never crosses one for you.

  1. DIRECTION gate ① 01 · /bob --brief

    Commit to a direction

    Read the memory first — a direction already refused is not reproposed. Five dimensions, approved as text, before anything is made.

    → direction brief
  2. CADRE gate ② 02 · /ray

    Frame the scope

    Written after the direction and against it, cut into lots of about 50 turns. Frozen at VALIDATED. Skipped in Sketch.

    → spec · lots · out of scope
  3. PRODUIRE 03 · /bob --proto

    Make it

    A clickable HTML prototype first, in every lane. Then Figma, then code if the module is on — a fresh bob-build per lot.

    → prototype · frame · code
  4. JUGER gate ③ 04 · /analyzer

    Two verdicts

    Conformance is a /20 the system computes. Direction is yours, binary. Never averaged — then the verdict is written to memory/.

    → verdicts + memory
  1. session 1
  2. state_<feature>.md
  3. session 2
  4. /pds reprendre
  5. session 3
  6. /pds reprendre
  7. session 4

Each gate writes the state to a file and the conversation ends. The next phase starts fresh from that file — nothing is re-read that it does not need.

↻ every judgment writes to the memory the next direction reads · EVE (research) and handoff are optional and never gate

05 The guardrails

A gate that only lives in a prompt holds until someone is in a hurry.

i.

The spec gate is enforced

A commit touching product code needs a Ref to a spec, and that spec has to be VALIDATED. Code without a frozen scope doesn't reach the branch — it goes back to RAY.

ii.

Constraints are checked, not hoped for

No any, no @ts-ignore, components under the line cap, a clean compile. Thresholds come from your own STACK.md, and the checks judge only the files you're committing.

iii.

Criteria are proven, not believed

Every acceptance criterion a machine can decide carries one assertion that BOB runs. Proven, unproven, or failed — "believed OK" is how defects slip through, so it isn't an option.

These are checked by running the stack on itself, and the failures are published alongside the passes — run 6 scored ~87/100 and found eight problems. 4.1 fixed the blocker and the three majors, each with its own targeted test. Read the self-test →

06 What you gain

Less rework.
More of the work that matters.

Rework isn't just wasted hours — it's wasted processing time and burned tokens. Every gate below exists to catch the wrong direction in text, before it becomes a generation you have to throw away. Before anything is built, RAY sizes the request into one of three tiers — so the numbers below are what shipping actually takes, start to finish, not a guess.

Time to ship, by tier

0 Tier 1 A small, isolated change — one component, one interaction, or a config tweak.
0 Tier 2 A standard feature with a full user flow — several screens or states working together.
0 Tier 3 A complex feature — new architecture, multiple stories, changes that touch several parts of the app.
0+/20 Conformance gate The minimum conformance score ANALYZER must give — and it's only one of two verdicts a feature needs.
ANALYZER scorecard /20
  • Spec conformance5

Conformance ladder
  1. 18–20Conforme
  2. 14–17Réserves — minor corrections
  3. 10–13Non conforme → back to BOB
  4. < 10Non conforme (critique) → back to RAY

Two verdicts gate the commit, never averaged. The score above is mechanical. The direction verdict is binary — retenue / refusée — and only the designer renders it. A delivery can score 20/20 and still be refused, as P-001 cycle 1 was. Only conformance ≥ 18 and direction retenue commits.

  • ✓ Creative judgment becomes enforceable architecture, not a suggestion.
  • ✓ Frozen specs kill scope creep before it starts.
  • ✓ A cumulative learnings database makes every cycle sharper.
  • ✓ Direction validated before development burns hours.
  • ✓ Atomic, per-step commits cut ambiguity and rollbacks.
  • ✓ Works with your stack — Next, Nuxt, SvelteKit, Astro, Remix.
  • ✓ Wrong direction caught in a brief, not in a build you have to discard.
  • ✓ Frozen scope means no regenerating a feature from a moving target.
  • ✓ One directed build pass, not an open-ended prompt-and-pray loop.
07 Why V5 costs less

We measured our own stack.
The chat was the bill.

The gates did their job. The cost came from somewhere else: everything that enters a conversation is paid again on every turn after it. So V5 throws the conversation away at every gate — the state lives in a file, and the next phase starts fresh from it.

The 4.1.x validation cycle — fresh install, Sketch lane

0M tokens read, in total the whole cycle, every session and every agent — measured with npm run tokens.
0 turns for bob-build against a budget of about 50 per lot. Run 6 hit the 80-turn cap four times in fifteen runs.
0 bob-build context, max no image read back — the guard blocks it before it reaches the context.
0 ADR-014 targets exceeded no session over 150k, the builder under 50 turns per lot.

What 4.1 changed

  • ✓
    The builder cannot read images — a guard in .claude/settings.json, scoped to bob-build, executed on three cases by check-parity at every release.
  • ✓
    RAY cuts a spec into lots of about 50 turns, and each lot gets a fresh bob-build. Nothing is resumed.
  • ✓
    The installer ships what its own CLAUDE.md tells you to run — memory/, scripts/, npm run memory:index and npm run tokens.
  • ✓
    components/ui/ is protected — a hand edit there is a blocker. Shadcn owns it.
  • ✓
    Effort where the judgment is — the direction on Opus at high effort, the build on Sonnet at medium.
  • ✓
    Verify in text, not pixels — Playwright CLI reads the page; one screenshot, for you, at the end.
